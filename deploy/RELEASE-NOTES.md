## 更新内容（0.4.13）

### 上游服务端计算接入改为按作者代能力判定

- 上游计算接缝此前对**所有**作者代无条件施加。但 `createServerScriptExecutor` 这套服务端计算分发机制
  自作者树 2.7.0 才引入；旧代没有它，硬造接缝只会得到跑不起来的代码，构建阶段就直接因锚点缺失失败。
- 现在按能力判定：作者树**不含** `createServerScriptExecutor` 时跳过上游计算注入（executor / worker /
  generation-tasks / storage 四项目标不生成，也不要求 `compute`/`readRuntimePolicy` 参数）；
  **含**时才施加。
- **反向护栏没有放松**：若作者树已有 `createServerScriptExecutor` 而接缝锚点缺失或重复，说明新版上游
  改坏了接缝点，仍然**响亮失败**，不静默跳过——否则计算权会悄悄落回页面，违反"唯一上游服务端计算"与
  "服务端不可用须失败/等待，不允许假成功或页面回落"。
- **必需锚点校验同样没有放松**：旧代虽不接上游计算，作者入口的开局分类锚点仍必须存在且唯一。
  缺失/重复一律拒绝，不因"这一代不接上游计算"而放宽准入。
- 客户端接缝 `applyUpstreamClient` 增加幂等守卫：二次施缝（同链重复安装 / buildCore 对比）不再报锚点缺失。

### 增量变更证据独立于读缓存生存周期（缺陷修复）

- **缺陷**：头部专用写路径（`patchHeadOnly`，即"第二刀"快路径）为省一次整档组装，只失效读缓存、
  不重建缓存条目；而增量变更帧（`recentChanges`）此前只存在于读缓存条目里。于是**连续头部写**——
  典型就是 `runtimeInputs` / 头字段这类 `path[0]` 不是 `messages` 的变更——之后，
  `changedIndices` / `readViewDelta` 会**永久**返回"无证据"，消费者只能全量读整档，
  `runtimeInputChanges` 这类细粒度证据实际作废。
- **修复**：把帧证据的生存周期从读缓存里拆出来（`changeFrames`）：
  - `forgetState`（数据失效：读缓存与帧一起清）与 `evictState`（仅回收读缓存：帧保留）分拆；
  - 读缓存被回收、或缓存未命中后冷读重载时，**不再清空既有帧**；
  - 帧链与当前 revision 不衔接时仍由连续性校验拒绝，回落全量读，**不会给出错证据**；
  - `rememberChanges` 增加首尾衔接校验，不相接时从头记录，避免断裂旧帧被无限拼接；
  - 帧表有独立条数上限，不会随档数无限堆积。
- 读缓存语义与"快路径不整档 assemble、不把整档放回读缓存"的护栏**均未改变**。

## 更新内容

- **前台队列源切点**：回退清理的队列切分按真实前台来源判定（`foregroundExact`），并透传到
  `cleanupAfterRollbackAtSeq`；首轮目标 prepend 到更早的独立队列时，独立队列保留，只清目标前缀。
- **同轮失败正文**：同一 operation 的失败收尾与重试保留真实发送前基准；回退资格不受终态或产物限制，
  错误/未确认旧轮必须先物理清理，之后才接受后继新发送，并记录新轮自己的基准。
- **Issue #15 B02–B10**：UTF-8 字节预算与 Unicode 安全分页、线性 Base64 校验、私有数据子树保护、
  同毫秒按 SQLite 写入顺序、事务内 revision/CAS、共享 TLA 求值 Promise、写前校验 `chat.id`。
- **PR16 维护只读输入**：工厂只读依赖随维护预演复制，不作为可写装配目标。
- **SQL 数值类型收口**：`version`/`messageCount` 先取 `json_type`，仅 `integer`/`real` 保留，
  布尔等一律 `null`。
- **本轮实际缺陷修复**：无实际写集时保持既有前像不变；完整与 SQL 窄读拒用其它分支前像；
  窄摘要严格匹配身份/版本/最新轮；冷窗口检查点标量阻止缺前像时走空尾兜底。
- **边界**：跨库**不声称原子**；"所有生产者无条件保证"**未达**，缺前像**不猜**、响亮拒绝。
